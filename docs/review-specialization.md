# 通用底座与分类专项审阅

审阅仍使用一套 LangGraph 流程及六个通用风险维度。现有 12 个默认合同类型各启用 4 个专项检查方向，共 48 个专项方向；加上共用的 6 个方向，配置目录合计 54 项。一次审阅只采用当前类型的 4 项专项方向，不会并行执行 12 套 Agent。

## 使用方式

1. 在合同管理或审阅表单选择并保存合同类型。后台优先采用文件保存的启用类型，阻止类型与请求不一致的启动；兼容“服务、服务采购、货物、工程”等旧名称。没有专项配置的自定义类型回退通用六维。
2. 正常启动后台审阅。任务创建后即可查看本次采用的类型、清单版本和检查方向，切换页面仍继续执行，停止流程不变。
3. 结果与历史中展开“本次审阅范围”，查看专项事项的核对说明和待补材料。历史保留当次快照，不因后来修改合同类型而改变。

| 核对状态 | 含义 |
| --- | --- |
| 检查方向 | 配置计划包含该方向，没有单独的完成记录，不能视为已核验 |
| 已核对 | 流程返回了有实际已读条款索引支撑的专项核对记录，可能发现问题，也可能认可已有安排 |
| 不适用 | 已读条款明确排除该事项，或完整阅读支持其不适用；不能仅因目录未命中而作判断 |
| 待补材料 | 相关条款、附件或依据不足，需要补充后复核 |
| 待核对 | 核对记录缺失、重复、格式不合法或引用了未读条款 |

这些状态记录审阅动作与资料覆盖，不构成合同合规或专业法律效果的保证。专项存在待补材料、待核对或遗漏项时，总结保持“审阅待补查”；空风险数组不会使专项自动完成。旧历史没有记录范围时不补造当前配置。

## 分类与实际执行

分类配置在 `backend/app/agent/review_profiles.py`，业务细则在 `backend/app/agent/prompts/contract_profiles/*.md`。检查项使用稳定 ID 和清单版本；修改清单含义时应提升版本。后台提示词可按原有配置机制覆盖，仍使用任务启动时的运行时快照；清单版本不是后台提示词记录版本。

- 每类定义相关检查项、所属通用维度及路由关键词。关键词只触发核对任务，不直接生成风险点。
- 保留六个通用维度；每个有专项内容的维度指定一次代表任务，对相关正文、附件引用和可能遗漏的安排进行核对。
- 专家收到专项清单与条款索引，使用现有 `get_clause` 补查正文。只有实际完整读到的条款才可作为核对索引；截断目录不能冒充已读正文。
- 专家在原 `risk_points` 之外返回 `check_results`，包含检查项 ID、状态、原因及已读索引。缺失、重复或未读索引不会被当作完成。根据全文不存在某事项判断不适用时，需要完整阅读；基于明确条款限定交易范围的排除，可标记 `basis=explicit_clause` 并给出依据。
- 质检继续验证原文、适用条件、证据和修改建议，已有法律条件与例外保护保留。通用提示词不再默认学校、供应商或采购角色，特别制度须由实际材料支持。

## 检索与知识边界

在原始通用查询外追加当前类型和相关检查方向的召回查询；三层知识库仍可参与召回，不按类型排除通用法规。最终排序保留原问题，并获得本次分类上下文。分类提示不传入关键法律条件识别作为交易事实，也不能变成证据。

查询改写保持通用模板，分类方向单独追加，避免按原问题缓存的改写在不同类型之间串用。模板工具采用任务绑定类型，不接受模型自行切换到其他类型。

本轮未新增或改写知识库法规语料，也未改变 golden qrels，不需要为此重建索引。当前语料不代表完整覆盖每个专业领域；缺少适用依据时继续待核实，不输出确定违法、无效或归属结论。

## 验证与后续效果验收

实施顺序、阶段门槛与结果见 [实施计划](review-specialization-plan.md)。离线测试使用模拟模型，验证类型绑定、提示词传参、路由、检索范围、核对记录约束、历史持久化及界面标签。修正测试全局客户端模拟，使预导入别名也受隔离。

真实模型遵循输出协议的稳定性、真实合同中的误报漏报、各行业资料完整性及专业人员审核仍需单独验收。本轮离线通过不能等同于这部分验收已完成。

更新前后端后使用，无新增数据库表、列或供应商依赖；部署前应结束或停止正在运行的任务，后端重启仍按原后台任务机制记录中断。
